# PRD 用语与定稿检查（prd-phrasing-audit）

> 与 **`@prd-spec`**、**`prd-writing-guard`**、**`@prd-writing-style`** 配合使用：本 skill 管**检查清单与结论口径**，不重写全文规范；具体 block / 截图 / hover 语法仍以 guard + spec 为准。

---

## 何时用

- 用户要求判断某段是否**定稿式需求**（而非解释性散文、环境说明、免责声明）。
- 用户要求**对照整篇 PRD** 看某章是否与概述、其它章**矛盾或漏项**。
- 用户要在标题后加 **（已检查）** 前，需要**先过一遍检查要点**。
- 用户说「用语检查」「过一遍定稿」「不要以上线为准那种」等。

## 何时不用

- 只改文风、删噪音、不动含义 → **`@prd-polish`**。
- 需要补写交互/逻辑、截图入库 → **`@prd-spec`**（及 **`.cursor/rules/prd-screenshot.mdc`**）等，本 skill 不代劳。

---

## 执行模式（强制 · 完整阅读 · 禁止抽检）

本 skill 的默认执行方式是 **对用户指定的审查范围做完整通读**，**不是**抽样阅读、不是「读一段就代表整章」。

1. **指定范围 = 最小完整边界**：用户若指向 **`## 第三章`**，则须覆盖该 `##` 下至下一同级 `#` / `##` 之前的**全部**小节与表格；若指向 **`### 2.1`**，则覆盖该标题下至下一同级 `###`（或更高阶 `#`/`##`）之前的**全部**内容。用户一次指定多个章节（如「第 2 章全部小节」）时，对**每一个**这样的边界各做一次完整通读。
2. **表格与块必须读完**：指定范围内的每一个 **`<!-- block:table -->`**（或等价结构化表格）须读完**全部 cell**（含设计列长状态说明、交互列每条 bullet、逻辑列全文），**不得**只读首行或抽样几格。
3. **禁止作为主结论依据的做法**（不足以支撑「用语检查已通过」或批量 **（已检查）**）：
   - 仅用 **grep / rg** 搜禁用词或章节号，未对照原文语境；
   - 只读章节**第一段导读**、只读**第一张表**、跳过 **`#####` 深小节**；
   - 「抽样几条 bullet 没问题」→ 推断整章通过。
4. **允许的技巧（不改变完整阅读义务）**：用 grep 仅作**定位锚点**（找到章节起止行号），读完仍须按文件顺序把指定范围内的正文**逐段读完**。若单次上下文放不下，**分批次 Read**，但批次之间须**衔接无遗漏**（按行号或标题连续覆盖）。
5. **与用户指令冲突时**：用户明确要求「只检查某一段 / 只检查表格交互列」→ 以用户缩小的范围为准，但仍须在该缩小范围内**完整读完**，而非抽检。

---

## 全文语义（强制 · 与「指定章完整读」同时成立）

指定章节须**单独读全**，但检查结论**不能**只建立在「这一章自洽」上；须同时核对 **整篇 PRD 是否仍说成一件事**。

1. **必读骨架（最低限度）**：除非用户明确声明「只核对本章字面、不看全文」，否则至少通读或回看：**文档标题与 `# 需求概述`（含需求功能清单若有）**；指定章内出现的 **「详见第 x 章 / x.x」** 所指段落是否**字面一致、无矛盾**。
2. **一致性核对**：指定章中的**命名**（页面名、能力名、字段名）、**范围边界**（写到哪里 / 不写什么）、**跳转与标签页约定**，是否与 **概述、清单、前后章节** 冲突或遗漏（例：概述列了能力清单正文未覆盖；正文写了准入概述说不准入）。
3. **交叉引用**：指定章若引用 **3.x / 4.x / 5.x**，须在脑中或文件中**对照目标节关键句**，避免「本章一句、他章反着说」。
4. **不代替全文再审**：本 skill 仍以用户**指定的检查范围**为主战场；「全文语义」是**附加闸**，不要求在未指定情况下把全文档每一字再审一遍，但**禁止**在明显未对照概述/他章的情况下断言「与全文一致」。

---

## 一、读全范围（强制）

与上文 **「执行模式」** 一致：完整边界内的正文须**读完**，不做抽检式抽样。

1. 用户指向某 **`#`～`######` 标题**或行号时，须读到该标题至**下一同级标题**之间的**全部**正文（含子标题、表格各列、列表、设计列状态说明），**不得**只读局部几十行就下结论。
2. 动笔或下结论前，先输出**一句结构摘要**（例：「该 `####` 下 1 个三列表、5 条交互小节」）。
3. **结合整篇**（默认建议执行，与上文 **「全文语义」** 一致）：核对 **需求概述 / 需求功能清单** 与目标章节的**范围、命名、章节号引用**，并对照**引用到的他章**关键句；目标仍是「指定章 + 全文不打架」。

---

## 二、定稿 vs 不合格用语（判断标准）

### 2.1 合格（定稿向）

- **行为可执行**：谁、在什么条件下、看到什么、点哪里、跳哪类页面（**当前标签页 / 新开标签页**按 guard 全局约定写清）。
- **范围边界**：本文写到哪里、**不**写到哪里（用产品词，不用「不另写实现规格」代替定义）。
- **与别章关系**：用「详见 **x.x**」「与 **x.x** 同源」等**文内章节引用**，不把评审责任甩给「上线后再对齐」。

### 2.2 不合格（须标出并建议改写）

| 类型 | 说明 | 处理方向 |
|------|------|-----------|
| **环境锚点** | **演示 / Demo / 本机 / 本地**（开发机语义）、**联调**、**mock**、**快照壳** 等绑定非交付环境 | 改为 **商家后台 / 顾客端 / 本期 / 配置侧** 等产品语境（见 **`prd-writing-guard`** 正文禁入第 8 条） |
| **工程坐标** | 项目路径、**具体 URL 路由**、**`4-15 主题发布页`** 类快照名、Demo 专用路径 | 改为 **主题发布页**、**样式设计**、**数据分析页** 等产品页面名 |
| **甩锅式对齐** | **以上线为准**、**以实装为准**、**以实现为准**、**本需求不另写实现规格** 等把定义推给「已有实现」 | 改为**可验收**的规则句，或明确写「沿用 **某功能页** 既有流程」等**产品承接**（不写变量名、不写壳名） |
| **编写元说明** | 「如有原型链接可汇总；**暂无则留空**」类**给作者看的占位** | 改为定稿：**本期无…** 或 **以正文设计列截图为准** 等**对读者**的一句话 |
| **解释性过长** | 大段背景散文占概述主体，清单与正文**语义拧巴**（例：表写「准入及过期」正文写「不做套餐准入」） | 拆短句；**表与正文同一结论** |
| **实现黑话** | 「钉合法像素 / 上游无原生 / 原样传 / 钉死接入点」等压缩术语，读者需猜实现 | 改成界面怎么选、背后实际怎么调的人话（见 **prd-writing-style → 换型类**） |
| **对照含糊** | 有后端/前端/官方文档可核时仍写「多为 / 视情况 / 以线上为准」；或把内部实现包装成商家新能力名 | 写清可核对事实；商家侧用人话写行为，不发明无入口的能力名 |
| **换型列不同构** | 「原型 / 现状 / 变更后」一侧密、一侧空，或多余实现备注段叠在已写清的映射表上 | 左右同构；够用就停；定稿不留活口（见 **prd-writing-style → 换型类**） |

### 2.3 与本需求沟通的**允许项**（不要误杀）

以下在**本需求（Loyalty 弹窗等）已定稿口径**中视为**产品表述**，**不要**仅因「像技术名」就建议删除；若其它文档无此约定，改动前**与用户确认**：

- **Shoplazza** 体系下，与会话 / 跨日去重 / 与数据章对齐相关的 **`sessionid`**、**`clientid`** 等写法（如 **2.1.4** 逻辑列「会话沿用…`sessionid`」「按…`clientid`…」）。

## 三、格式与 guard 对齐（指定范围内逐项核对）

- **`前端计算：`**：凡写「由前端算出的展示字段」，须有 **`前端计算：` + 公式 + 取整/边界`**（见 **`prd-writing-guard`** / **`@prd-spec`** 交互列约定）。
- **`hover`**：交互列固定 **`- **【hover 文案】**：`** + 全文。
- **逻辑列**：无页后规则则**留空**；**交互穷尽**见 **`prd-spec`** **「五 → `逻辑` 列 → 交互穷尽」**——泛指望位句仅适用于整格再无 bullet；若下方仍有顾客端/统计等小节，首句须**点名交互已覆盖范围**再写不重述；若交互已穷尽而后文仍为逻辑列复述同一套可见链路 → 标冗余。
- **禁止入正文**的其余条：**Agent 流程**、**组件名/变量名**（本需求**除外**见上节 **`sessionid`/`clientid`**）、**渲染/CSS 实现指导** 等 → 一律对照 **`prd-writing-guard`**「正文禁入内容」。

---

## 四、检查后交付（强制 · 建议先行 · 不经确认不改文）

1. **默认行为**：检查结束后，只输出 **一条条修改建议**（可加序号）；每条尽量包含 **位置**（章节号 / 小标题 / 表格大致位置）+ **问题** + **建议改法**（可附替换句示例）。**不在用户确认前**对仓库内 PRD **`.md` 做任何写入**（不用 apply_patch / Write 改正文）。
2. **用户确认后**：用户回复「按建议改」「第 x 条改掉」「可以改了」等明确指令后，再逐条或批量修改正文。
3. **例外（可直接改）**：用户当轮**明说**「检查后直接帮我改」「发现问题你就改」→ 可在同轮完成修改；若建议多项，仍建议先列出再改，避免 silent 大 diff。
4. **与本 skill 冲突的旧约定**：凡此前写法暗示「检查后可顺手改文」，以本条为准：**默认不改**。

---

## 五、（已检查）标记纪律（与用户约定一致）

1. **只有**在完成**「执行模式」通读** + **「全文语义」核对** + **「二」「三」** 后，且用户若采用「建议先行」，须在用户**确认修改落地之后**，才在正文标题上加 **（已检查）**；或用户声明「本章审核结论已通过、允许标记」后再加。**禁止**在仅有「待确认建议」时在正文批量加 **（已检查）**。
2. **禁止**：抽样几段、或只 grep 关键词未读表内全文，就给整章或各小节标题批量加 **（已检查）**。
3. 用户若要求**每个小标题**都标记：应对 **`###` / `####` / `#####`** 等**每一个**该通读的标题分别完成检查后再加；**大节通过 ≠ 各小节已通过**。
4. 若用户已确认修改并已写入正文，可在同轮说明**改了哪些条建议**；存在未解决的硬伤 → **不加** **（已检查）**，或从误标标题上**移除**。

---

## 六、输出格式（建议）

对用户回复时建议包含：

1. **结论**：指定范围 **通过 / 需修订后通过 / 不通过**（简短说明主因）。
2. **与全文一致性**（默认给出）：至少一句——概述 / 清单 / 引用到的他章 **是否**与指定章矛盾或遗漏。
3. **修改建议清单**（如有）：**一条条**列出，便于用户逐条回复确认；勿合并成一大段散文。
4. **下一步**：明确写「确认后我可按清单改正文」或等待用户指令。

---

## 七、与现有 skill 的分工

| Skill | 分工 |
|--------|------|
| **`@prd-phrasing-audit`（本 skill）** | 用语是否定稿、指定章是否合规、**是否与全文语义一致**；默认只出建议；**（已检查）**须经确认或用户豁免 |
| **`@prd-polish`** | 在含义不变前提下收写法、删噪音 |
| **`@prd-spec` + `prd-writing-guard`** | 结构与硬协议的唯一权威 |
| **`@prd-writing-style`** | 文风、换型类「原型/现状/变更后」、人话技术映射 |

---

## 八、不做的事

- **不**替代 **`prd-writing-guard`** 成为全文规范源；冲突时以 **guard + 用户当轮口头约定**（如 **`sessionid`/`clientid`**）为准。
- **不**在未读全指定范围时给「本节已无问题」式结论。
- **不在未经用户确认（或无明确「可直接改」指令）时修改 PRD `.md`**。
- **不**为通过检查而编造与真实 UI 不一致的交互（若涉及 UI 核实，仍按 **guard** 的优先级：截图 / DevTools / 浏览器等）。
