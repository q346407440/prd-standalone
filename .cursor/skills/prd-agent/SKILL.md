# PRD Agent

> 写 PRD 时 `@prd-agent`，然后用自然语言说你要做什么。

---

## 零、角色与边界（最高优先级）

**当用户 `@prd-agent` 时，你进入 PRD 写作模式，必须遵守以下规则：**

1. **只读业务代码，不改业务代码**：为理解已实现功能，你可**只读**业务源码，路径包括：**(a)** `../`（当 `prd-standalone` 作为子目录放在业务仓库内时，父目录即业务根）；**(b)** Cursor **多根工作区**内与用户 PRD 任务**并列、用户已关联**的其他项目根（例如工作区里除 `prd-standalone` 外的另一个文件夹）；应主动结合用户 `@` 引用、对话中的项目名或语义搜索定位这些目录。**绝不修改**业务项目中的任何文件。你能写入的文件范围**仅限** `prd-standalone/` 目录内：
   - `pages/doc-NNN/*.md` — PRD 正文
   - `pages/doc-NNN/*.meta.json` — 展示元数据
   - `pages/doc-NNN/*.annotations.json` — 标注数据
   - `public/prd/` — 截图资产
   - `pages/.active-doc.json` — 激活文档索引（通过 API 操作）
2. **不要修改项目配置与源码**：`src/`、`vite.config.js`、`package.json`、`.cursor/`、`feishu-sync-server.js` 等均不在写作范围内。
3. **不要把 PRD 内容写入业务代码**：PRD 正文、注释、说明性文字不能写进业务项目（含 `../` 或多根工作区内的关联仓库）的任何文件。
4. **如果用户让你修改业务代码**：提醒用户"当前处于 PRD 写作模式（@prd-agent），如需修改业务代码，请在不携带 @prd-agent 的新对话中操作"。

## 〇·一、写 PRD 表格前合规清单（每次改表先过一遍）

> **为何单独放一节**：规则在「四 / 五 / 七」等处仍有完整说明；本清单是**高信号摘要**，减少「只记住半截」导致的格式跑偏。**仅靠调整 SKILL 章节顺序**对 Agent 帮助有限；**在「零」之后立刻放可执行清单**比单纯挪章节更有效；详细规则仍在后文各节。

动笔修改或新增 **三列表格**（`设计/原型稿 | 交互 | 逻辑`）前，在内心按下列项**逐项确认**（写完后可再扫一遍）：

1. **表格语法**：单元格内**一般正文**（交互 / 逻辑 / 设计列叙述、bullet）**换行只用 `<br>`**，**禁止**在叙述性内容里随意插入真实换行符（会弄坏标准 GFM 表格行解析）。**例外**：嵌入 **`:::mermaid:::` … `:::end-mermaid:::`** 或 **`:::mindmap:::` … `:::end-mindmap:::`** 时，**代码本体可占多行**，续行规则见 **「六 → Mermaid 图表 block」** 下「表格单元格内」。**表头与表体之间的分隔行一律用最短合法写法**（见 **「五 → PRD 正文中的 GFM 表格（表格外层）」**）：三列表为 `| --- | --- | --- |`；**禁止**用一长串 `-` 与表头「视觉对齐」。
2. **列举子项必换行（交互列、逻辑列相同）**：只要在写**多条子项**（并列要点、多个配置项、多条件、多级归属），**每条单独成条**，条与条之间用 `<br>` 衔接；**禁止**用顿号「、」或分号把多条子项挤在同一行里串完（详见 **「五 → 表格单元格内交互 / 逻辑列共用规则」**）。**交互** 列**禁止**写作元说明（如「本段侧重…」「与…互补」），**说明文案** 下只写定稿句（详见 **「五 → 交互列不写的内容 → 『说明文案』小节写法」**）。
3. **hover / 说明气泡定稿（强制）**：字段旁问号、帮助图标、悬停 / 聚焦出现的说明气泡，以及 **`title` 等仅悬停可见的定稿句**（若本节要求写入 PRD），在 `交互` 列中一律写为 **`- **【hover 文案】**：` + 定稿全文**（全角冒号须在闭合 `**` 之后，以便编辑器内 markdown-it 正确加粗），句末用句号；**禁止**写成 **说明**（…）用括号包裹全文。与 **`**说明文案**`** 小节（卡片内整段只读说明正文）**不是同一类**，勿混用标签。详见 **「五 → hover / 说明气泡定稿（交互列）」**。
4. **交互 / 逻辑列换行密度（强制 · 首次写表即遵守）**：凡模块含**多个字段、多段界面行为或多条页后规则**，**默认**按「**加粗区块标题** → 一级 `-` → 必要处 **`  - `（两空格缩进）**」展开；**同一字段**若需写清控件、**【hover 文案】**（若有）/ 其它并列信息、取值范围 / 步进等，**必须**拆成多条子行，**禁止**挤成单条超长 bullet；**逻辑** 列中多条独立规则**禁止**用分号「；」串在同一条 `-` 内。**不得以省篇幅为由**压成一句。版式参考仓库正文 **2.1.4**（交互 / 逻辑列）。详见 **「五 → 表格单元格内「交互 / 逻辑」列共用：换行与子项列举（强制）」**。
5. **设计列边界**（详见 **「七 → 设计列只放截图与链接」** 与模板）：仅 `![](/prd/xxx.png)`、`**场景预览：**`、`**状态说明：**`、`[打开真实页面](可访问的 URL)`；**不写**流程解释、注意事项、链接说明等 PRD 外的废话。
6. **截图流程**（详见 **「七 → 启用检测」「七 → profile 占用重试」「七 → 67% 标准成图法」**）：需要新图或需打开本机 Demo 查看页面时，**先**按 **「七 → 启用检测（强制）」** 检查用户是否已配置 **Chrome DevTools MCP**；**若已配置且可用，固定使用** 该 MCP 完成 **打开页面、查看、视口截图** 等步骤，**不得**首选其它浏览器 MCP；**若已配置但连不上**，**先**按 **「七 → profile 占用重试」** 再试，**仍失败**再备选 Browser。**入库的设计列截图必须在浏览器页缩放 67% 下完成**（`Meta+0`/`Control+0` 复位后连续 **4 次** `Meta+-`/`Control+-`，地址栏显示 **67%**）；**禁止**为成图把页缩放调到 **100%** 或任意非 **67%**（与后台观感对齐以 **67%** 为唯一规格）。**标准方法**（唯一）：**视口 `take_screenshot`（不传 `uid`）** + **`evaluate_script` 读取 `getBoundingClientRect()`** + 按 **`PNG 像素宽高 ÷ window.innerWidth / innerHeight`** 换算 **本机裁切**（`sips` / Pillow 等）写入 `public/prd/`。**禁止**使用 DevTools **`take_screenshot(uid)`** 成图（在强制 **67%** 下必出问题或不可靠，见 **「截图工具优先级」**）。**绝对定位下拉**等与主容器分离的浮层：对 **主容器与已展开子面板（如 `.moc-prereq-hover-wrap--open .moc-prereq-hover-panel`）** 的 rect **求并集**后再裁切，可略加 **padding** 保留阴影。成图前对目标 **`scrollIntoView`**；需隐藏 Demo -only 控件时可 **`evaluate_script` 注入 `<style>`**（如隐藏 `.moc-prereq-panel-demo-btn`），**不得**改业务源码。**禁止** **`document.documentElement.style.zoom`** 与页缩放混用。备选 `cursor-ide-browser` 时 **同样强制 67%**，用 **`browser_get_bounding_box`（快照 ref）+ 视口 PNG 按同一比例裁切**。壳层索引等允许整视口成图但仍须 **67%**；灰边处理见 **「画幅与留白」**。
7. **写回粒度**（详见 **「四、写回约束」**）：最小单位 **单行 / 单 block**；默认**只改** `交互` / `逻辑`，除非用户明确要求改 `设计/原型稿`。
8. **逻辑列**：无页后系统规则时 **整格留空**，不用「无」「—」占位（详见 **「五 → 仅交互、逻辑留空」**）。**禁止**用实现向套话填满 **逻辑** 列（详见 **「五 → 逻辑列禁写」**）。
9. **正文语言**：PRD 正文用 **简体中文**；`block` 标记与 `.cursor/rules/prd-writing-guard.mdc` 一致。
10. **链接**：「打开真实页面」须为**本机已校验可开**的完整 URL，禁止猜端口、猜 path。
11. **禁止占位符与字母代词（`交互` / `逻辑`）**：**禁止**用 **N**、**X**、**C/B**、**YYYY-MM**、**ID** 等字母或格式占位指代业务概念；**必须**写**能直接读懂的中文概念名**（同一含义全文用同一短语，可加粗）。**顾客端 / 商家后台**等端侧用中文，**禁止**写 **C 端 / B 端**。例外与示例写法详见 **「五 → 正文用语：禁止占位符与字母代词」**。
12. **初稿即简洁（防累赘）**：**第一次落笔**就按 **「五 → 初稿即简洁：如何避免交互 / 逻辑列先天累赘」** 取舍——交互 / 逻辑**不重复叙述**、能 **详见** 则不重写、区块下控制 bullet 数量；**不是**「先写冗稿再压缩」的事后删字流程。
13. **同一 `block:paragraph` 内多行正文**：若**仍属同一段落**（不拆成多个 `block:paragraph`），直接换行即可——解析器会把 `<!-- block:paragraph -->` 到下一个 block 标记之间的所有行收入同一个 block；**行间不留空行**（空行会触发拆分为多个 paragraph block）。与**表格单元格**内用 `<br>` 不同，勿混用。详见 **「六 → `paragraph`：同一段落内多行」**。

## 〇·二、文档自动创建

用户可能直接说"帮我写一个 xxx 的 PRD"，但 `pages/` 下还没有任何文档，或用户想要的文档还不存在。此时你需要**主动帮用户创建文档**：

1. **检查现有文档**：调用 `GET /__prd__/list-docs` 查看已有文档列表。
2. **判断是否需要创建**：
   - 如果已有文档且用户意图是修改现有文档 → 直接编辑对应 `.md`
   - 如果没有任何文档，或用户明确要新建一个文档 → 执行创建
3. **创建文档**：调用 `POST /__prd__/create-doc`，body 为 `{ "name": "<文档主文件名>" }`（不含 `.md`）。文件名规则与仓库根目录 `shared/prd-filename-sanitize.js` 中 `toSafeDocBaseName` 一致：允许**中文、英文、数字**及 `.` `_` `-`，禁止 `\ / : * ? " < > |` 与控制字符，最长 80 个 Unicode 码点；Windows 保留名（如 `CON`、`AUX`）会自动加 `_文档` 后缀。用户用中文描述需求时可直接使用中文主文件名（如「会员弹窗」→ `会员弹窗`）。
4. **创建成功后**：API 返回 `{ ok: true, slug, title, mdPath }`，你随后读取 `mdPath` 对应的 `.md` 文件，开始按 PRD 格式写入内容。

> 注意：`create-doc` API 运行在 `http://127.0.0.1:6001`，你通过 Shell 工具用 `curl` 调用即可：
> ```bash
> curl -s -X POST http://127.0.0.1:6001/__prd__/create-doc \
>   -H 'Content-Type: application/json' \
>   -d '{"name":"member-popup"}'
> ```

## 一、仓库关键路径

> 本项目（`prd-standalone`）通常作为业务项目的子目录使用（如 `my-project/prd-standalone/`），因此 `../` 就是业务项目的源码根目录。AI 应主动读取父目录的源码来辅助撰写 PRD。当本项目独立使用时，业务代码路径由用户在对话中指定。

> **多根工作区（通用）**：用户常把 `prd-standalone` 与业务项目**并列**加入同一 Cursor Workspace（兄弟文件夹，而非嵌套）。此时业务代码**不在** `prd-standalone/../` 下，而在工作区内的**其他根目录**。你应将这些**与用户当前 PRD 主题相关的项目**视为可读业务源码：主动用工具读取、搜索，或跟随用户 `@文件夹/文件`；**写入与改 PRD 仍只在 `prd-standalone/` 内**。若用户未指明哪一个是业务项目，可根据对话中的产品名、路由、仓库名与工作区文件夹名对齐后再读。

> 多文档架构：每个 PRD 文档对应 `pages/doc-NNN/` 目录，目录内以文档名命名的 `.md`、`.meta.json`、`.annotations.json` 三个文件始终同名。当前激活文档的 slug 记录在 `pages/.active-doc.json`。

- `pages/<slug>/<文档名>.md`：PRD 正文，是当前文档的唯一真相。
- `pages/<slug>/<文档名>.meta.json`：仅展示元数据（图片宽度、Mermaid 视图模式与宽度、Mindmap 视图模式与宽度），不参与需求语义。
- `pages/<slug>/<文档名>.annotations.json`：可选增强输入，不是主流程硬依赖。
- `public/prd/`：截图资产目录（所有文档共享）。
- `../`：业务项目源码（仅当 `prd-standalone` 嵌套在业务仓库内时），AI 应主动探索此目录了解已实现的功能。
- **工作区内关联项目根目录**：多根工作区并列时，业务代码所在的其他文件夹根；通过用户 `@`、对话提示或搜索定位，**只读**。

## 二、数据源优先级

1. 用户当前消息里的明确要求与自然语言描述。
2. 业务项目的真实源码与运行中的页面状态（嵌套场景默认探索 `../`；并列多根工作区则探索**工作区内关联项目根**，或用户本轮指定路径 / `@` 引用）。
3. 用户补充文档、`docs/` 下的说明文档、现有 PRD 正文上下文。
4. `<文档名>.annotations.json`，仅在用户明确要求"按标注来"或需要精确圈定局部时启用。

冲突处理：
- 可见 UI / 前端状态 / 字段展示 / 默认值 → 以真实运行页与源码为准。
- 页面上看不到的逻辑 / 条件 / 后端规则 → 结合用户自然语言与补充文档。
- Demo 与文档对可见行为冲突 → 以 Demo 为准；隐藏逻辑冲突 → 先向用户确认。

## 三、默认触发行为

- 用户说"写 PRD""按我的 PRD 套路写"→ **先过「〇·一、合规清单」**（含第 **3** 条 **hover / 说明气泡**、第 **4** 条 **换行密度**、第 **11** 条 **禁止占位符**、第 **12** 条 **初稿即简洁**），再读当前激活文档的 `.md` 结构，以本地 Demo 为主生成 **`交互`**，**首次成文即按「一级 `-` + `  - `」分行**，**禁止**索引式长句；**说明气泡类定稿**用 **`- **【hover 文案】**：`**（见「五 → hover / 说明气泡定稿」）。**存在页后系统规则时再写 `逻辑`，否则 `逻辑` 整列留空**（见「五、列职责」之「仅交互、逻辑留空」）。**同时默认为每个含交互内容的新增模块截图并补充设计列**（见「七、设计列截图与链接」）。
- 用户说"补截图""补设计列""补跳转地址"→ 自动启用设计列截图流程（见「七、设计列截图与链接」）。
- 用户说"按标注来"→ 将 annotations 提升为本轮主增强输入（见「八、Annotations 增强输入」）。
- 用户给了新的 Demo 项目路径或地址 → 以该项目为本轮主 Demo 源。

## 四、写回约束

- 写回时必须保留 `<!-- block:type -->` 标记、Markdown 表格结构与图片路径格式。
- **GFM 表格分隔行**：新建或改写 PRD 中**任意** Markdown 表格时，分隔行用**最短合法** `---` 段（如三列 `| --- | --- | --- |`）；**禁止**仅为对齐表头宽度而加长 `-`（与渲染无关，徒增行长与 diff）。细则见 **「五 → PRD 正文中的 GFM 表格（表格外层）」**。
- **多个 `block:h1`**：允许且常见于长文档骨架（见「六 → 可选：章节序号 → 常见文档骨架」）。除文档名外，下一大块通常为 `# 需求概述`；勿与 `.cursor/rules/prd-writing-guard.mdc` 中「全文仅一个 h1」的旧理解混淆——以本 SKILL 与 guard 表格为准。
- 最小写回单位是**单个表格行**，不改目标行以外的 block。
- 默认只改 `交互` / `逻辑` 列；只有用户明确要求时才改 `设计/原型稿` 列。
- `cellStates.<column>.changeIntent='unchanged'` 与历史 `locked=true` 都视为默认不改写。
- 文案必须使用简体中文，优先采用"加粗小标题 + bullet / ordered list"结构。
- 信息不足时保守撰写，不发明未确认规则；待确认项必须给出推荐值，格式为「xxx 待确认，推荐 xxx」；若涉及取值范围，同时给出推荐的最小值、最大值与默认值（如「取值范围待确认，推荐 0–60s，默认 3s」），让审阅者只需修改而不需要从头思考。
- **行业通行方案**不需要「待确认+推荐值」形式，直接写定稿结论。判断标准：该行为在同类 SaaS 产品中有一致的业界共识（如「选择全部」选中当前可见项、「清除」全部取消选中），则视为通行方案，直接描述。
- **禁用「以现网为准」**：这个表达含义模糊，容易误导开发去参考线上旧版本。需要指向具体参考对象时，用以下替换：
  - 视觉/布局/文案样式 → **「以设计稿为准」**
  - 数据接口/字段口径 → **「以接口文档为准」**
  - 业务规则/枚举值 → **「以产品约定为准」**
- **大块下的多子模块**（一个功能区块下含多个配置子块）：父级用 `<!-- block:h3 -->` + `###` 三级标题；每个子模块再缩进一层，用 `<!-- block:h4 -->` + `####` 四级标题，其下接 `<!-- block:table -->` 独立三列表格。便于在目录与编辑器里区分「整块」与「子模块」；除非用户明确要求合并，不要把多个子模块挤在同一张表的多行里。
- **Demo 页面链接**：写入 PRD 前须按第七节「本地 Demo 页面链接如何获取」校验真实可访问的 `href`，不得凭记忆或猜测端口。

## 五、列职责

### `交互` 列

- 只写**需求功能**在**商家后台配置界面**上的可见、可操作部分：字段、控件、行为与定稿文案（与设计列截图、说明文案一致）。
- **入口 / 导航 / 能力卡跳转**（无表单字段、仅「从 A 进入 B」）：仍属交互范畴——用一句话概括模块性质，再分点写 **入口** 所在页面、点击对象、进入的 **目标页** 名称（上述用 `**加粗**` 即可）；与同页其它入口的差异若影响理解可写一句。**此类模块若无页后系统规则，`逻辑` 列留空**（见下节），**不要**为填满逻辑列而写入口路径约定、路由策略、示意图与形态说明的复述。
- 优先采用"先用一句话概括本次变更性质，再分点展开"的结构。
- **【】用法**：**仅**界面上的 **按钮**、**链接式 CTA**（如 **【返回】**、**【保存配置】**、**【去配置××】**、**【重置默认】**）使用直角引号 **【名称】**。**区块小标题**（如 **模块定位**、**内容要点**）、**字段名**、**Tab / 分段名**、**卡片标题**、**活动子类型名** 等一律 `**加粗**`，**不**套【】。**唯一例外（PRD 标签，非界面按钮）**：**hover / 说明气泡定稿**在 `交互` 列中必须使用固定标签 **【hover 文案】** + 全角冒号 + 定稿全文；**Markdown 源文件须写为** `- **【hover 文案】**：` + 定稿句（**全角冒号在闭合 `**` 之后**），规则见下节 **「hover / 说明气泡定稿」**——**不得**因「【】仅用于按钮」而改为 **说明**（…）括号形式。
- **输入框的取值限制（最小值、最大值、默认值、单位、字符数上限等）属于交互列**，不写到逻辑列；待确认的限制以「取值范围待确认，推荐 x–x，默认 x」形式标注在对应输入框描述里。
- **可选枚举条目（下拉选项、多选列表项等）**——直接把所有可选项写进交互列；枚举本身即定稿范围，**不需要另外补一句「与字典对齐」「数据来源待确认」「新增类型是否自动进入」**——那些是开发实现细节，不是 PRD 要解决的问题。

#### 交互列不写的内容

1. **截图已能表达的**：结构、布局、控件位置、视觉样式——截图看得到的不用文字复述。
2. **设计稿标注职责的**：元素排列顺序、间距、按钮位置——这是设计稿的工作，不是 PRD 的工作。
3. **开发实现细节**：数据来源、字典对齐、不可用项的渲染规则（灰显与否）、新增类型是否自动进入列表——这类问题的答案隐含在交互列已定稿的枚举与行为里，开发阶段照着做即可，不需要在 PRD 正文里单独说明。
4. **顾客端展示条件与状态分支**：「未安装 / 已安装时展示不同内容」「是否登录」等**根据条件走不同展示路径**的规则——这类判断属于后端逻辑或顾客端渲染逻辑，写进**逻辑列**；**交互列**只写**商家后台配置界面**上可见、可操作的需求功能（字段、控件、说明文案等）。
5. **写作元说明 / 结构自述**：不解释「本段侧重什么」「与某某模块互补」「引导句与分句的分工」「本节与下一节如何分工」等——这类话描述的是**文档写法或章节关系**，不是产品需求。PRD **交互** 列只写**产品事实**（展示什么、配置什么、操作什么、定稿文案是什么）。若需与另一节对照，用**节号交叉引用**（如「详见 **2.1.2**」）或依赖**设计列截图**，**不要**在正文里写抽象分工句、互补句、元概括句。

##### 「说明文案」小节写法（与 **2.1.2** 等章节对齐）

- **何时用**：模块内有一段**与界面定稿一致、供配置方阅读的说明**（与 **清单行**、**分类入口**、**预览示意** 等并列）时，用加粗小节标题 **`**说明文案**`** 单独成块。
- **写什么**：**只写定稿句子**——可直接面向界面逐条写清「是什么 / 在什么条件下 / 建议配置什么 / 带来什么效果」（多条并列时用多条 `- `，一条一意）；与 **2.1.2** 一致时，可按业务侧分组（如 **积分获取活动** 侧 / **积分消耗活动** 侧）再分条。
- **不写什么**：不在 **说明文案** 下先写一句「总起元说明」（例如「首段为定稿策略说明，侧重…；与…互补」）——属上条 **写作元说明**，**禁止**写入 PRD 正文。
- **与其它小节的关系**：**模块定位**、**卡片结构** / **清单行**、**说明文案**、**预览示意** / **操作与跳转** 等小节按模块真实结构拆分即可；**不要**额外用一条 bullet 解释「说明文案与预览示意如何分工」。

##### hover / 说明气泡定稿（`交互` 列 · **强制**）

> **适用**：配置页上通过 **问号 / 帮助图标**、**悬停或聚焦**触发的说明气泡（及与本节口径一致、需写入 PRD 的 **`title` 悬停句**）。**不适用**：卡片内整段只读说明正文——那些归 **`**说明文案**`** 小节，用普通加粗分条即可，**不要**套 **【hover 文案】**。

- **写法（固定）**：在对应字段或区块下用子行写 **`- **【hover 文案】**：`** + **完整定稿句**（句末句号）。**一条气泡一条子行**（推荐独占一条一级 `-`）。**禁止**写成 **`**【hover 文案】：**` 紧接正文**（`：**` 与后续汉字直接相连时，本仓库编辑器所用 **markdown-it** 无法解析加粗，会露出字面量 `**` 或被序列化为 `\*\*`）。**禁止**写成 **说明**（…）用半角括号包裹全文。
- **示例**：`- **【hover 文案】**：用您店近30天会员进店停留做的参考（每周更新），帮您看个大概：晚一点再弹窗，还有多少会员可能还在页面上，方便调「弹窗首次弹出时间」。仅供参考，非实时。<br>`
- **与图表悬停浮层**：曲线 / 热区等 **鼠标悬停** 出现的**独立浮层文案**在 `交互` 列中按行为描述（**鼠标悬停** … 展示「…」），句中须用**可读中文**指代量（如「进店后若干秒 · 预估可触达约若干人」），**禁止**用 **X / N** 等字母占位；若该浮层与某 **【hover 文案】** 同源且只需一处定稿，可只写行为句并交叉引用字段侧 **【hover 文案】**，避免重复粘贴。**若与整数秒配置字段（如「弹窗首次弹出时间」步进 1 秒）联动，浮层中的秒数须在 PRD 中写明为**整数秒**（展示用秒数），不得要求界面展示小数秒。**

##### 正文用语：禁止占位符与字母代词（`交互` / `逻辑` · **强制**）

- **禁止**用 **单字母**、**英文字段缩写**、**格式占位串**（如 **N**、**X**、**C/B**、**YYYY-MM**、**ID** 等）承载业务语义；读起来像「代称猜谜」，不符合 PRD 可读性要求。
- **必须**使用**能直接读懂的中文概念名**；同一指标在全文**用语一致**，可加 **`**加粗**`** 建立「术语锚点」（如 **「抵扣 1 美元所需积分数」**），**禁止**同义反复时改用字母。
- **端侧称呼**：写 **顾客端**、**商家后台**（或与团队统一的 **消费者端** / **管理端**），**禁止**写 **C 端 / B 端**。
- **例外（窄）**：（1）**产品界面或品牌**中客观存在的英文（如 **Loyalty**）、合法 **URL**、币种单位等；（2）**完整示例**中可出现具体数字与分隔符（如 **2026-04**、井号），但对**命名格式**的文字说明仍须用中文拆解各段含义（如「四位年份、短横线、两位月份」），**禁止**单独用 **YYYY-MM** 这类纯占位教读者猜。
- **公式与运算**：用中文动词（如 **除以**、**乘以**）配合上述**中文术语**，**禁止**写成 **「A ÷ N」** 式字母公式；必要时可另起一句用**阿拉伯数字举例**验算。

##### 业务概念与后台字段（`交互` / `逻辑` · **推荐**）

> **为何单独放一节**：同一规则可以写成「业务语义」或「表单项校验」两种抽象层级；本仓库正文（如 **2.1.2**）约定**优先概念层**，避免只堆字段否定式长句。

- **优先**用**业务/产品概念**说清「在管什么」（如 **会员生效范围**：活动对哪些会员生效），**再**用**半角括号**与后台字段名或界面标签对齐，例如 **会员生效范围**（**适用会员**），便于评审与实现对照。
- **字段级表述**指：直接对着某个配置项写**可执行条件**（如「**适用会员** 不得为『全部会员』」）——适合写在概念已明之后的**细化句**，**不宜**单独一条里叠多重否定（如「不适用…非…」），以免歧义。
- **概念层表述**指：先写判定维度（如「须 / 不做 **会员生效范围** 判定」），再展开条件（如「**会员生效范围**（**适用会员**）不是『全部会员』」）——**优先**用于 `逻辑` 列规则与索引表口径。
- **否定句**：若某类型**不做**某类判定，**直述**「**不做会员生效范围（适用会员）判定**」即可，**避免**「不适用『…非…』类判定」等曲折嵌套（见上条）。

##### 初稿即简洁：如何避免交互 / 逻辑列先天累赘（**写作习惯**）

> **本节是「第一次落笔」的取舍原则**，用于**从源头上**减少冗长与重复；**不是**「先写长文再删」的事后压缩步骤清单。

1. **列边界先划清**：`交互` 只写**界面上可见、可操作**的事实；`逻辑` 只写**页后**判定、存储、换算、频控、过滤。**禁止**把同一句意思在两侧各写一遍（改几个同义词也算重复）。
2. **能「详见」则不重写**：与他节完全重复的口径，只写 **「详见 ×.×.×」**；本节仅保留**只在本模块才成立**的增量信息。
3. **加粗小节下控制条数**：每个区块标题（如 **模块定位**、某 **字段名**）下，默认 **少量**一级 `-` 即够（非字段拆解需要时，**不**为「看起来完整」堆叠同义句）。
4. **定稿与解释分工**：界面 **说明文案**、**【hover 文案】**（Markdown 写 **`- **【hover 文案】**：`**）、引号内**定稿句**——**照抄定稿**；「系统怎么算、何时刷新」等**一条逻辑 bullet** 收束，**不要**在 **交互** 里复述算法全文。
5. **禁止写作元说明**：不写「本段侧重」「与下节分工」「索引待补」等自述（与 **「交互列不写的内容」** 一致）；信息不足时用 **「以产品约定为准」** 并给**推荐值**，**禁止**用占位废话撑篇幅。
6. **多字段卡以字段名为轴**：每个配置项单独成条，下面只挂控件、取值、定稿；**禁止**一条 bullet 从左上扫到右下「流水账」描述整张卡。

#### 表格单元格内「交互 / 逻辑」列共用：换行与子项列举（**强制**）

> **团队约定（与产品书写习惯对齐）**：**凡是在列举子项，就要换行分段**——**交互列**与**逻辑列**同一标准；差别只在「写什么内容」（见各列职责），**不换行、不串顿号的版式要求一致**。

> **强制（首次 `@prd-agent` 写 PRD 即须遵守）**：进入 PRD 写作模式后，**新建或改写** `交互` / `逻辑` 单元格时，**默认**按本节执行；**不得以篇幅、初稿、先写索引再细化**等理由输出「一条 bullet 塞满多字段 / 多规则」的长句。**多字段配置模块**（如一张卡内多个输入项、图表多段行为）须采用 **仓库正文 2.1.4** 式结构：**字段名单独一条一级 `-`**，其下用 **`  - `** 分行写控件形态、**【hover 文案】**（若有）、取值与步进等。**逻辑** 列中**每条独立规则**单独一条一级 `-`，**禁止**用分号「；」串在同一条内。

- **何时算「列举子项」、必须拆行**：同一格内出现**多条并列**的说明、配置项、条件分支、跳转入口、规则条目等，凡读者需要按「第一条 / 第二条…」扫读的，即视为列举——**一条 `- `（或 `1.`）只承载一条子项**，**每条末尾 `<br>`**，下一条再写新的 `- `（或序号）；**不要把多条子项写进同一句里用「、」连接**。
- **层级子项**：确属上一条的子集时，用 **`  - `**（两空格 + `-`）另起子行，**每行仍 `<br>` 结尾**；不要滥用缩进。
- **区块标题与正文**：加粗小标题（如 `**模块定位**`、`**主区自上而下**`）后**紧跟 `<br>`**，再开始第一条 bullet 或段落。
- **有序列举**：需要顺序时用 `1.` `2.` …，**每条后 `<br>`**，规则同上。
- **例外（极窄）**：全格仅**一句**极简枚举、无带 **【】** 的按钮名、无附加说明时，可写「可选：A、B、C」类**同一 bullet 内短句**；**一旦出现需逐项扫读的字段名 / 配置项（如 `**字段名**`）或带 `**【按钮文案】**` 的项，必须改为一项一行**。
- **设计列**以第七节模板为准（截图 + 场景 + 状态 + 链接）；多句说明同样用 `<br>` 分段，但不按本节拆 bullet。

#### PRD 正文中的 GFM 表格（表格外层）

> **适用范围**：需求正文里**所有** GFM 管道表格（含三列需求表、功能清单表等），不限于 `交互` / `逻辑` 单元格内格式。

- **分隔行（表头下一行）**：每栏**至少三个连字符**即可；**默认一律写最短形式**，例如三列：<br>`| --- | --- | --- |`<br>N 列则 N 段 `---`，段间仍用 `|` 分隔。
- **对齐（可选）**：若需指定列对齐，仅在对应段上加冒号（GFM 标准），**仍保持每段字符数最少**，例如 `| :--- | :---: | ---: |`；**不要**在冒号旁再堆叠多余 `-` 去凑宽度。
- **禁止**：为与上一行表头单元格「对齐」而把分隔行拉成极长一串 `-`（历史文档或编辑器自动生成常见）；新写与改写时**统一改回最短写法**。
- **说明**：长短两种分隔行渲染结果相同；最短写法可减轻编辑器卡顿、便于 diff 阅读。

#### 交互列 Markdown 写法规范

表格单元格内的格式约定（**交互 / 逻辑 / 设计列叙述**仍**全部用 `<br>`** 分段，不用真实换行；**列举子项的规则见上节「交互 / 逻辑列共用」**。**Mermaid / Mindmap 代码块**不在此限，见 **「六 → Mermaid 图表 block」「六 → 思维导图 block」** 中「表格单元格内」）：

- **区块标题**：`**标题**` 加粗，之后紧跟 `<br>` 换行，再开始 bullet。
- **一级 bullet**：`- 内容`，表示该区块下的一条配置项或字段说明；**一条 bullet 只写一条子项**，多条则多写多条 `- `，条间 `<br>`。
- **子级 bullet（有层级归属时）**：`  - 内容`，用两个空格缩进 `-`，表示上一条 bullet 的枚举选项或子集；**仅在内容确实是上一条的子集时才缩进**，不要滥用缩进。
- **表格图片（禁止行内图文混排）**：**禁止**在同一 text 段内把说明文字与 `![](url)` 写成「一句里的行内混排」。图片须**独立成段**：与前后文之间用 `<br>` 分段（即一格内多段里，图独占一段，与 5.1 类版式一致）。**原因**：飞书同步对 `cell.elements` 仅在 `type === 'image'` 时插入图片；`text` 内的 `![](...)` 会被剥离，行内混排会导致丢图。本地解析会对表格格做 `splitMarkdownByInlineImages` 规范化，旧稿行内图在载入后会拆成 text / image / text，存盘后与规范形一致。**勿**在反引号行内代码中写完整 `![](...)` 图片语法（首版匹配不区分代码 span，可能被误拆；见 `prd-inline-image-split.js`）。

示例对照：

```
**展示频次**<br>
- 提供 **展示频次** 下拉框，可选：<br>
  - 仅展示 1 次<br>
  - 每 1 次<br>
  - 每天 1 次<br>
  - 每 7 天 1 次<br>
  - 每 30 天 1 次<br>
**停止推送条件**<br>
- 提供 **设置停止推送条件** 复选框；<br>
- 勾选后展示条件下拉：<br>
  - **弹出指定次数后**（展示次数数字输入 +「次」）<br>
  - **点击后**（不展示次数输入）
```

### `逻辑` 列

- **没有系统规则时留空**：逻辑列只写「系统判断 / 计算 / 存储 / 生效 / 数据过滤 / 状态流转」等页面上看不到的规则。如果一个模块只是「展示什么文案、提供什么入口」，没有任何隐含的系统逻辑，逻辑列**直接留空**，不要为了填满而把交互内容复述一遍。
- 只写字段、状态、条件、历史数据处理、后端规则。

#### 逻辑列禁写（非产品定义的「逻辑」）

下列内容**不得**为撑篇幅、显得「完整」而塞进 **`逻辑` 列**——属于实现惯例、设计说明或与 **交互** 列重复的校验，**不是**须单独成文的页后**业务规则**（与用户对「逻辑」的常规定义不一致时，以**留空或删**为准）：

- **设计与工程实现细节**：如「以 design token 为准」、派生色公式、控件级配色在代码中的映射方式等——**不写进** **逻辑** 列。
- **配置端非法值回退、合成预览的兜底算法**：**交互** 列已写清取值范围、枚举或默认值的，**不再**在 **逻辑** 列复述「非法时回退为某某」。
- **存储兼容、字段别名合并**：如旧字段键名并入新键、避免双写等，除非产品明确要求**配置方或审阅方**必须知晓，否则**不写**。
- **空泛持久化套话**：仅「保存后与顾客端一致」「加载失败详见某节」而**无本节独有增量规则**时，**不写**——改由 **交互** 列 **与保存** 一条 **详见** 或页级统一约定承接。

**整格留空**：本节不存在须写清的「顾客端何时生效、与哪些条件叠加、数据口径、频控 / 准入、后台过滤」等**产品规则**时，**`逻辑` 单元格保持空白**（不用「无」「—」占位）。

#### 仅交互、逻辑留空（导航 / 入口 / 能力卡）

适用：**本模块在商家后台界面上仅有导航类操作**（如点击 **【返回】** 或菜单 / 能力卡等进入另一页），**没有**要在本格展开的默认值策略、频控、准入（权限以外）、数据合并、异步回填、状态机等页后规则。

- **表格形态**：仍使用三列表格（`设计/原型稿 | 交互 | 逻辑`），**`逻辑` 单元格保持空白**即可；不要用「无」「暂无」「—」等占位符硬填。
- **写作边界**：「主路径以本入口为准」「直链不作为约定入口」「静态配置 / 接口下发」等——若属于**实现细节或路由说明**，默认 **不写进 PRD**；若确属**需求文档必须写清的导航约定**（配置方须据此理解入口），**合并进 `交互` 一句或一条 bullet`**，**不要**单独占满 `逻辑` 列。
- **示例（与仓库正文风格对齐）**：**样式设计** 页上 **会员权益弹窗** 能力卡——`交互` 写概括句 + **入口卡片** 下列出并列关系、点击整卡进入 **会员权益弹窗编辑器**；`逻辑` **留空**。（**【】** 仅用于该页面上真实的按钮 / CTA 文案时。）
- 需要顺序时用 `1.` 有序列表，不需要顺序时用 bullet。
- 页面上看不到的逻辑，优先结合 `docs/` 与用户描述补充。
- **换行与子项列举**：与 **交互列完全一致**，一律遵守上一节 **「表格单元格内交互 / 逻辑列共用：换行与子项列举」**——**列举子项即每条单独成行 + `<br>`**，禁止用顿号、分号在同一条里串多条独立规则。
- 逻辑列同样遵循：**区块标题**加粗 + `<br>`，子集用两空格缩进 bullet，**每条 `<br>` 收尾**。
- **同一区块下若有多条独立规则，必须拆成多条一级 `-`，每条 `<br>` 换行分隔**；不要用一条 bullet 里用分号串起多条规则，避免与交互列的可读性不一致。
- **不要写「可选列表与 xx 字典对齐」「枚举项有哪些」「列表顺序与枚举一致」等商家后台界面上已能直接看到的枚举类描述**——这类内容放在交互列；逻辑列只写顾客端判断、接口/数据口径、与其它模块叠加等页面上不直接展示的规则。
- **不写 Demo 调试约定与接入层实现细节**：如「本地 Demo 用 localStorage 模拟…」「正式环境由接入层写入 key…」「可在接口返回后由接入层写入同名 key 便于联调」等——这类内容是前端实现惯例，不是产品需求，不属于 PRD 任何列；这类说明只能出现在 Demo 源码注释或内部开发文档中。

#### 选择器弹窗的逻辑只写这三项

当一个 PRD 模块包含「选择器弹窗」或 **页面内多选面板**（如选择活动、选择折扣、选择页面类型等），逻辑列**只补充页面上看不到的规则**，不要写通用弹窗行为（取消/关闭/重置/翻页/加载/异常等），也**不要重复写已在交互列写过的枚举与列表展示**。

**判断一条内容属于交互列还是逻辑列：** **商家后台配置界面**上能直接操作、看到或做出选择的——都写交互列；包括「选择全部」「清除」等面板内的操作按钮行为，即使它们看起来像「规则」，只要操作与结果在界面上可见，也属于交互列。

1. **数据范围 / 准入条件**：仅当存在 **后台隐藏过滤**（界面上看不全来源）时在此说明；若可选条目已全部展示在配置页，只在交互列描述即可。
2. **特殊筛选项的逻辑**：仅当筛选规则无法从界面操作直接推断时在此说明；通用「按名称关键字过滤可见行」可写在交互列。
3. **排序逻辑**：仅当排序依赖后台规则且与界面展示顺序说明无关时在此说明；若只是「与枚举顺序一致」写在交互列。

## 六、变更语义

| 关键词 | 适用场景 | 写作要点 |
|--------|---------|---------|
| `全新功能` | 全新的页面、模块或完整功能链路 | 直接从功能目标开始描述 |
| `原页新增` | 在现有页面上新增入口、字段、按钮、卡片、配置项 | 聚焦新增内容，显式写"新增" |
| `功能迭代` | 已有功能的交互、逻辑或规则增强 | 显式写"调整 / 更新 / 补充"，不要写成全新功能 |
| `沿用现状` | 本次不改动的区域 | 表达保持原样即可 |

若用户有固定文风，优先服从用户文风。

### 纯逻辑内容不用三列表格

当一个小节**没有任何需要在三列表里展开的界面级需求功能**（无可配字段、无可截之图），只是表达一条全局规则、内置前提或系统约定时，**不需要用三列需求表格**，直接用 `### 标题` + 正文段落表达即可。

**适用场景举例**：
- 「固定受众：仅登录用户触发」——无配置项，纯系统内置规则 → 用 `paragraph`
- 「顾客端触发判断流程」——多条件分支逻辑，开发需要看清判断顺序 → 用 `mermaid`
- 「活动内容失效与活动状态的关系」——开发需要理解的系统约定，无商家后台配置项 → 用 `paragraph`

**格式**（`paragraph`）：标题多为 `h3`；在「需求概述」等 h1 大段下也可直接用 `## 小节`（block:h2）+ `paragraph`（如 `## 1. 目的 / 背景`）。
```md
<!-- block:h3 -->
### 标题

<!-- block:paragraph -->
正文内容（bullet 或段落均可）。
```

#### `paragraph`：同一段落内多行

当需要在**同一个** `<!-- block:paragraph -->` 里写多行连续正文，且**仍视为同一段落**（对应编辑器里「同一段 / 同一输入框」语义、不拆成多个 paragraph block）时：

- **换行写法**：直接换行即可，**不需要**行尾 `\` 或其他特殊语法。解析器会把 `<!-- block:paragraph -->` 到下一个 `<!-- block:xxx -->` 标记之间的所有行收入同一个 block 的 `markdown` 字段（以 `\n` 分隔）。
- **行间不留空行**：多行之间**不得**插入空行；空行会触发 `expandParagraphBlocksOnBlankLines` 将其拆分为多个独立 paragraph block。
- **与表格区分**：GFM **表格单元格**内叙述换行仍用 **`<br>`**（见「〇·一」第 1 条）；本规则仅适用于 **`block:paragraph`** 下的自由正文。

```md
<!-- block:paragraph -->
**小标题或首句**
第二行接续说明（仍属同一段）。
第三行同理。
```

**格式**（`mermaid`）：
```md
<!-- block:h3 -->
### 标题

<!-- block:mermaid -->
\`\`\`mermaid
sequenceDiagram
    ...
\`\`\`
```

不要为了「格式统一」强行填一张空的三列表格，或把逻辑塞进某行的逻辑列里勉强对应。

### Mermaid 图表 block

当需要在 PRD 中嵌入流程图、时序图等可视化图表时，使用 `<!-- block:mermaid -->` + 标准 Markdown fenced code block 语法：

```md
<!-- block:mermaid -->
```mermaid
graph LR
  A[开始] --> B[结束]
```（结尾三个反引号）
```

- Mermaid block 可作为顶层 block（与 paragraph、table 同级），也可作为表格单元格内的 element。
- 表格单元格内的 mermaid 以 `:::mermaid:::代码:::end-mermaid:::` 格式存储（因 GFM 表格内不支持 fenced code block）。
- **表格单元格内（多行写法 · 与「〇·一」表格语法例外对齐）**：
  - **推荐**：`代码` 部分按 Mermaid 习惯**多行**书写（每语句一行），便于阅读与 diff；语义与「单行 + 分号」等价时优先多行。
  - **续行规则**：**每一「逻辑表格行」仍以 `|` 开头**；在某一列中写完 `...<br>:::mermaid:::` 后，**后续代码行不得以 `|` 开头**，解析器会把这些行并入同一条表格行，直至出现 **`:::end-mermaid:::`**；**该行以 `:::end-mermaid::: |` 收尾**（闭合标签后空格 + 行尾 `|`）。
  - **勿**在叙述段落中混用裸换行代替 `<br>`；仅 **`:::mermaid:::` … `:::end-mermaid:::`** 包裹的代码区使用真实换行。
- Mermaid 视图模式（代码 / 图表）和显示宽度存储在 `<文档名>.meta.json` 的 `mermaidViewModes` 和 `mermaidWidths` 中（主键为块稳定 id：`mermaid_s_${blockId}` / 表格内 `mermaid_t_…`，旧版按代码 hash 的 `mermaid_*` 仍可读作回退），不影响 md 正文。**默认**为 **仅展示图表**；切换视图后 **立即** 写入 meta（避免仅依赖 debounce 导致刷新丢失）。

### 思维导图 block

当需要在 PRD 中嵌入思维导图时，使用 `<!-- block:mindmap -->` + **Markdown 缩进列表**（`- ` 开头，两空格缩进表示子级）：

```md
<!-- block:mindmap -->
- 根节点
  - 子节点 A
    - 孙节点 A1
    - 孙节点 A2
  - 子节点 B
```

**书写规范**：
- **必须**使用 Markdown 缩进列表格式（`- 项目`），**不要**使用 Mermaid mindmap 语法（`mindmap\n  root((...))` 形式）。
- 前端会自动检测误用的 Mermaid mindmap 语法并转换为 Markdown 列表，但为避免不必要的数据变更，请直接使用正确格式。
- 缩进用**两个空格**表示一层子级。

**适用场景**：展示需求功能结构全貌，让开发一眼看清本需求涉及哪些主要模块，放在章节开头。

- Mindmap block 可作为顶层 block（与 paragraph、table 同级），也可作为表格单元格内的 element。
- 表格单元格内的 mindmap 以 `:::mindmap:::代码:::end-mindmap:::` 格式存储（因 GFM 表格内不支持缩进列表）。
- **表格单元格内多行**：与上节 Mermaid **相同的续行规则**（首行 `|`、代码续行不以 `|` 开头、以 `:::end-mindmap::: |` 结束该行）；列表代码仍用 **`- ` + 两空格缩进** 表示层级。
- Mindmap 视图模式（代码 / 图表）和显示宽度存储在 `<文档名>.meta.json` 的 `mindmapViewModes` 和 `mindmapWidths` 字段中，不影响 md 正文。

### 小节标题命名规范

- **格式**：`大模块名-子模块路径-功能名`，各段之间用 `-` 连接，一律使用**纯中文**，禁止夹入英文技术术语（如「Loyalty & Push」「前置与门控」）。
- **正确示例**：`会员弹窗-活动创建-折扣配置-自定义`、`会员弹窗-折扣配置-Loyalty 安装判断`（仅在没有合适中文替代时保留品牌名，但标题整体仍以配置路径语义为主）。
- **应避免**：在标题里使用「门控」「前置条件」「判定」「安装检测」等系统设计语言；换成**需求 / 配置路径上可读**的中文描述，如「是否已安装 Loyalty 的说明与开关」。

#### 可选：章节序号（与 `h2` / `h3` / `h4` 对齐）

- **何时用**：文档较长、需要固定阅读顺序或评审指位（如「按 2.1.3 改」）；同一父级下**自上而下强顺序**的配置块（如编辑器内多张卡片）特别适合带号。并列、可能频繁插队的模块可只用路径式命名、不加段内序号。
- **常见文档骨架（可按需采用）**：首行 `# 文档名`（block:h1）→ `# 需求概述`（block:h1），其下用 `## 1. 目的 / 背景`、`## 2. 需求功能清单`、`## 3. 原型图汇总`、`## 4. 设计图汇总`（均为 block:h2，各自可接 paragraph / table）→ 再接 `# 产品详细功能说明`（block:h1），其下功能大章用**另一套**序号从 1 递增，如 `## 1. 需求入口`、`## 2. 会员权益弹窗编辑器`…。**注意**：`buildTableBindings` 按文档中 `h2` 出现顺序绑定表格；若某表前无对应 `h2`，会落在占位 slug（如 `section-1`），一般无设计列截图标注；「需求概述」下的 `## 2. 需求功能清单` 若含表，其 `tableKey` 会带 `2-需求功能清单` 前缀，与「产品详细功能说明」下的表相互独立。
- **`##`（block:h2）**：在**同一父级语境**内阿拉伯数字 + 英文句点 + 空格 + 标题从 1 递增。「需求概述」下为 1～4；「产品详细功能说明」下功能章重新从 1 递增（如 `## 1. 需求入口`、`## 2. 会员权益弹窗编辑器`）。
- **`###`（block:h3）**：`父 h2 章节号.本级序号` + 空格 + 标题，例如 `### 1.1 …`、`### 2.1 会员弹窗-编辑器-页面层级框架`。
- **`####`（block:h4）**：若 `h4` 是某个 `h3` 下的**顺序子模块**，用**三级编号**：`父h3号.本级序号`，例如 `h3` 为 `2.1` 时，子块依次为 `#### 2.1.1 …`、`#### 2.1.2 …`。同一文档内**同一层级编号规则保持一致**。
- **维护**：插入新节时顺延其后序号；合并或删除章节后应整体核对编号，避免断号与重复。若变更带序号的 `h2` 标题，需同步核对 `<文档名>.annotations.json` 里与 `sectionTitle` / `tableKey` / `rowKey` / `usageId` 相关的条目（或由编辑器 reconcile 后人工确认）。

## 七、设计列截图与链接

**何时触发**：凡新增含交互内容的模块（无论用户是否口头说「补截图」），**默认执行截图并补充设计列**；不需要用户额外提醒。

**设计列只放截图与链接**：设计列的单元格内只允许出现截图 `![](/prd/xxx.png)`、场景 / 状态说明标注（`**场景预览：**`、`**状态说明：**`）、以及「打开真实页面」链接；**不放任何流程解释、注意事项、链接说明等文字性说明**——那些内容属于 SKILL 文档本身，不属于 PRD。

**截图工具优先级**：在满足下文 **「启用检测（强制）」** 的前提下，**固定 Chrome DevTools MCP**；**已配置但连不上**时 **先**做 **「profile 占用重试」**，**仍不可用**再按 **「备选：Cursor 内置 Browser」** 执行；**未配置**则直接备选 Browser。**设计列入库截图一律在页缩放 67% 下完成**；**禁止**为成图使用 **100%**（含「对照成图」「觉得清晰改 100%」等均不允许）。**禁止**使用 **`take_screenshot(uid)`** 作为设计列入库成图（Chromium 在 **67%** 等页缩放下常把节点盒映射到错误像素，出现扁条、裁到预览区等；本 SKILL **强制 67%**，故 **不采用 uid 成图**）。**唯一标准方法**：**视口 `take_screenshot`（不传 `uid`）** + **`getBoundingClientRect` + 按比例像素裁切**（下文 **「67% 标准成图法」**）。**禁止** **`style.zoom`** 与页缩放混用。备选 Cursor **`cursor-ide-browser`** 时 **同样强制 67%**，裁切逻辑与 Chrome 路径一致。

### 启用检测（强制）：Chrome DevTools MCP

在执行任何 **打开本机 Demo 页面**、**查看页面结构 / 文案**、**设计列入库截图** 之前，**必须先**检查用户 Cursor 是否已配置并启用 **Chrome DevTools MCP**（常见 MCP server 名：**`user-chrome-devtools`**；部分环境显示为 **`chrome-devtools`** / **Chrome DevTools** 等，以 **Settings → Tools & MCP** 中实际列表为准）。**检测方式**（至少一种即可）：**（1）** 打开 **Cursor → Settings → Tools & MCP**，确认列表中存在上述服务且已启用；**（2）** 查看工作区 **`.cursor` / MCP 工具目录**（如 **`mcps/user-chrome-devtools/tools/`**）下是否存在 **`navigate_page`、`take_screenshot`、`evaluate_script`** 等工具描述 JSON。

- **若已配置且可用**：**固定**使用 **Chrome DevTools MCP** 完成 **打开页面、导航、快照、视口截图、`evaluate_script`** 等全部相关步骤；**不得**将 **`cursor-ide-browser`** 或其它浏览器 MCP 作为**首选**。
- **若未配置、未启用**：再使用 **「备选：Cursor 内置 Browser」**，并仍遵守 **67% 标准成图法**。
- **若已配置但连接失败 / 启动报错**：**不要**立刻降级为备选 Browser；**先**按下文 **「profile 占用重试」** 排查并 **重试** MCP；**仍失败**再使用 **「备选：Cursor 内置 Browser」**，或按本节 **「执行步骤」** 对设计列注明 **截图待补**（见 **`.cursor/rules/prd-screenshot.mdc`** 摘要）。
- **若用户在本轮对话中明确要求**仅用某一浏览器 MCP：以用户当次指令为准，但仍须满足 **67%** 与 **视口 PNG + rect 裁切**（或等效）规则。

### profile 占用重试（Chrome DevTools MCP 连不上时优先执行）

典型报错形如：`The browser is already running for .../chrome-devtools-mcp/chrome-profile`。**不是**网络故障，而是 **同一 user-data-dir 已被 Chrome 占用**，MCP 无法再启第二实例。

**处理顺序（Agent 可照做）**：

1. **先关** MCP 自动打开的那类 Chrome 窗口（若仍可见）。
2. **结束占用该 profile 的 Chrome 进程**（只杀带 MCP profile 的实例，**不要** `killall Google Chrome` 误杀日常浏览器）：
   - macOS 示例：`pkill -f "user-data-dir=.*/chrome-devtools-mcp/chrome-profile"`
   - 或：`ps aux | grep chrome-devtools-mcp/chrome-profile`，对**主进程** `kill <PID>`（子进程通常会随主进程退出）。
3. **重试** MCP：`list_pages`、`navigate_page` 等应恢复正常。

**仍失败**时的备选顺序、禁止为截图安装 Playwright 等，与 **`.cursor/rules/prd-screenshot.mdc`** **「Chrome DevTools MCP『连不上』」** 及 **「禁止为截图安装额外自动化栈」** 保持一致。

### 优先：Chrome DevTools MCP（设计列截图默认）

设计列需要**真实页面截图**时，在通过 **「启用检测」** 后，**必须**使用 **Chrome DevTools MCP**（MCP server 名一般为 `user-chrome-devtools`，以 **Settings → Tools & MCP** 中实际启用的名称为准）。工具名以各版本描述为准，常见包括 `list_pages`、`new_page`、`select_page`、`navigate_page`、`wait_for`、`press_key`、`take_snapshot`、`take_screenshot`、`evaluate_script`、`click` 等。

### 67% 标准成图法（模块 / 局部截图 · 强制）

> **适用范围**：绝大多数「设计列模块图」；**成图与审阅观感以 67% 为唯一真相**，与配置端常见缩放对齐。  
> **核心**：先 **67%**，再 **整视口 PNG**，再用 **CSS 像素 rect ×（PNG 像素 ÷ 视口 CSS 宽高）** 在本机裁出入库。

**硬性顺序（缺一视为不合规）**：

1. **`list_pages` / `new_page` / `select_page`**：打开本机 **业务 Demo** 真实 URL（`npm run dev` 的终端 **Local** 端口为准；`ERR_CONNECTION_REFUSED` 则先启动业务项目 dev）。
2. **`wait_for`**：等到页面关键文案出现，避免白屏截图。
3. **页缩放强制 67%（成图前必做 · 唯一允许的最终成图缩放）**  
   - **必须先完成本步**，再截视口、再读 rect。  
   - **做法**：`press_key` **`Meta+0` / `Control+0`**（复位缩放阶梯），再连续 **4 次** **`Meta+-` / `Control+-`**（Chromium 典型：**100% → … → 67%**）。  
   - **禁止**：为入库 PNG 将页缩放留在 **100%** 或其它比例；**禁止** **`take_screenshot(uid)`** 作为模块成图手段。  
   - **禁止**：同时使用 **`document.documentElement.style.zoom`**（或任意 CSS zoom）与上述页缩放。  
   - **验收**：地址栏旁页缩放显示 **67%**。
4. **（可选）页面状态**：`evaluate_script` 清/写 **`localStorage`**、`navigate_page` **`reload`** 等，使目标 UI 态出现；**不得**改业务仓库源码。  
5. **（可选）隐藏 Demo 控件**：`evaluate_script` 注入 **`<style>`**（如 `.moc-prereq-panel-demo-btn{display:none!important;}`），仅影响当前页会话。  
6. **滚动入屏**：`evaluate_script` 对目标容器 **`scrollIntoView({ block: 'center', inline: 'nearest' })`**；需 **`click` 展开菜单** 时，在 **67%** 下 **`take_snapshot` → `click(uid)`** 后再取 rect（**不要用 uid 截图**）。  
7. **读取裁切框（与截视口同一时刻）**：`evaluate_script` 返回 JSON：  
   - **单块模块**：目标元素 **`getBoundingClientRect()`** → `left, top, width, height`；  
   - **含绝对定位下拉**：对 **`.moc-editor-shell-alert-bundle`（或等价根）** 与 **`.moc-prereq-hover-wrap--open .moc-prereq-hover-panel`** 等 **分别取 rect，求并集**（`min(left)`、`min(top)`、`max(right)`、`max(bottom)`），可整体 **扩 padding（如 6px）**。  
   - **同时返回** **`window.innerWidth`、`window.innerHeight`**（与 rect 同为 **CSS 像素**）。  
8. **视口截图**：**`take_screenshot`** **不传 `uid`**，`format: png`，`filePath` 指向临时路径或仓库路径；此为 **整视口** 位图。  
9. **本机按比例裁切**：设 PNG 宽高为 **`pngW, pngH`**，则  
   `sx = pngW / innerWidth`，`sy = pngH / innerHeight`，  
   `cropLeft = floor(rect.left * sx)`，`cropTop = floor(rect.top * sy)`，`cropW = floor(rect.width * sx)`，`cropH = floor(rect.height * sy)`，**钳制在 PNG 范围内**后 **`PIL.Image.crop` / `sips -c`** 写入 **`…/prd-standalone/public/prd/xxx.png`**。  
10. **annotations**：按 **最终入库 PNG** 实际宽高更新 **`*.annotations.json`** 的 `width` / `height`。

**说明**：**`take_snapshot`** 仅用于 **定位可点击元素**（展开下拉等），**不**用于 **`take_screenshot(uid)`** 成图。**`fullPage: true`** 仅用于明确需要纵向长页的节，且仍须在 **67%** 下截取后再按需要裁切。

**Cursor Browser**：**67%** 同上 → **`browser_take_screenshot`（视口）** → **`browser_get_bounding_box`（快照 ref）** 得到框 → 按 **`视口 PNG 像素 / 视口 CSS 尺寸`** 换算裁切（与上式同构）；**勿**把快照 **`ref`** 误传给 **`browser_take_screenshot` 的 CSS `ref`** 参数。可用 **`browser_resize`** 在 **67%** 下收窄宽度减灰边（见「画幅与留白」）。

### 备选：Cursor 内置 Browser（`cursor-ide-browser`）

在 **「启用检测」未通过**（Chrome DevTools MCP 未配置 / 未启用）、**连接失败且已按上文「profile 占用重试」仍失败**、或 **用户明确要求仅用 Cursor Browser** 等情况下使用。

- **开启能力**：Cursor **Settings → Tools & MCP → Browser Automation**，打开 **Browser Automation**（模式以本机为准）。
- **工具**：MCP server 名一般为 `cursor-ide-browser`（`browser_navigate`、`browser_snapshot`、`browser_take_screenshot`、`browser_get_bounding_box`、`browser_press_key`、`browser_lock` 等）。
- **与 Chrome 对齐：页缩放强制 67%**（`Meta+0`/`Control+0` + 4×`Meta+-`/`Control+-`），再 **`browser_take_screenshot`（视口）** + **`browser_get_bounding_box`（快照 ref）** 按 **「67% 标准成图法」** 同公式裁切；裁切异常时 **收窄视口**（`browser_resize`）或重取 rect，**禁止**改 **100%** 成图。
- **侧栏 / 分屏**：`browser_navigate` 的 `position: "side"`（或等价参数）。
- **官方说明**：[Browser 工具](https://cursor.com/docs/agent/tools/browser)。

### 截图选区原则（模块 PRD 默认：容器面板 DOM）

> **与「写哪一节、截哪一块」对齐**：表格通常对应文档里的一个 **功能子模块**（多为 `h4` 下的一行）。为该模块写设计列时，截图应优先覆盖 **该模块在页面上的「容器面板」DOM**——即包住这一块功能的**最贴切外层**（如整张配置卡、告警条区域、带标题的分区 wrapper），而不是整页视口，也不是单个按钮 / 单行输入。前端应对齐 **需求相关父容器**（如 React 组件根节点：`div.moc-editor-shell-alert-bundle` 等），使截图边界与实现一致。

- **DevTools / 用户给出的矩形（优先互证）**：若用户粘贴 **DOM Path、组件名与 `Position: top/left/width/height`**（或等价 `getBoundingClientRect`），应视为 **该模块根容器** 的权威范围；在 **强制 67%** 下用 **「67% 标准成图法」** 第 7～9 步（视口 PNG + rect 换算裁切）框住该容器；**禁止** **`take_screenshot(uid)`**。**Cursor** 路径在 **同 67% 视口** 下用 **`browser_get_bounding_box`** 与视口 PNG **按像素比例**裁切。
- **默认（DOM 定位）**：**Chrome**：**67%** 下 **`evaluate_script`** 对 **`[role=region][aria-label=…]`** / **`.moc-editor-shell-alert-bundle`** 等取 **`getBoundingClientRect`**，配合 **视口 PNG 裁切**（**「67% 标准成图法」**）。**Cursor**：**67%** 下 **`browser_get_bounding_box`（快照 `ref`）+ 视口 PNG 按比例裁切**；**勿**依赖 **`browser_take_screenshot` 的 CSS `ref`** 传快照 `e71`（语意不同，易整页成图）。
- **`ref` 语意分叉（易错）**：在 `cursor-ide-browser` 里，**`browser_click` / `browser_get_bounding_box` 等**使用的 `ref` 是 **快照里的不透明句柄**（如 `e71`）；**`browser_take_screenshot` 的 `ref` 按工具 schema 为 CSS 选择器**，不能把 `e71` 当成截图目标传入。若元素截图仍落成整视口，用 **`browser_get_bounding_box`（快照 `ref`）+ 视口截图后按框裁剪** 作为可靠兜底。
- **整页 / 壳层截图（例外）**：仅当本节 PRD 明确是 **整页结构、编辑器壳、路由级索引**（例如「整页结构」「页面层级框架」类 `h4`）时，才使用 **视口截图** 或 **壳 + 主区** 级画面，帮助建立全局导航印象。
- **禁止**：为省事截全屏导致目标模块只占一角；**禁止**只截单行控件、孤立图标作为该模块的唯一设计图（除非该节就只描述这一控件且用户明确要求）。

### 执行步骤

1. **默认路径：Chrome DevTools MCP**  
   严格按上文 **「67% 标准成图法」** **步骤 1～10**（**强制 67%**、视口 PNG、**`getBoundingClientRect` 按比例裁切**）；落盘 `public/prd/xxx.png` 并更新 annotations 像素。

2. **备选路径：`cursor-ide-browser`**（**「启用检测」未通过**，或 **DevTools 已配置但经「profile 占用重试」仍不可用**时）  
   - `browser_lock`（若需）→ `browser_navigate` 真实 Demo URL → `browser_wait_for` 首屏稳定。  
   - **页缩放强制 67%**：`Meta+0`/`Control+0` + 4×缩小键（与 Chrome 路径一致）。  
   - **`browser_take_screenshot`（视口，勿传错 `ref`）** + **`browser_get_bounding_box`（快照 `ref`）** → 按 **「67% 标准成图法」** 第 9 步同构公式裁切 → 写入 `prd-standalone/public/prd/xxx.png`。  
   - **禁止**为定位改业务源码；**禁止只截单行控件**；**禁止 100% 成图**。

3. **画幅与留白（禁止整图大片空白）**：视口截图时，若视口远大于 **67% 下**实际排版宽度，会出现**右侧、下方大块灰边 / 空画布**。**模块级设计图**须 **按容器 rect 裁切视口 PNG**（**「67% 标准成图法」**），通常可同时避免「模块过小」与「留白过大」。
   - **验收标准（模块截图）**：成图应以 **该节对应的模块容器面板** 为主角，面板外留白在宽、高任一方向不宜超过约 **5% 画幅**。**整页 / 壳层索引截图**则以 **侧栏 + 顶栏 + 主内容区** 等业务 UI 为主角；若明显超出，必须重截或裁剪后再入库。
   - **Chrome / Cursor（67%）**：一律 **`getBoundingClientRect` / `browser_get_bounding_box` + 视口 PNG 比例裁切**；**禁止 `take_screenshot(uid)`**。
   - **Cursor · 兜底**：`browser_get_bounding_box`（快照 **`ref`**）+ 视口 PNG 按 **`pngW/innerW`、`pngH/innerH`** 裁剪。
   - **收窄视口**：在 **已与 Chrome 对齐的页缩放** 前提下，`browser_resize` 使侧栏 + 主区少留白（宽度常见 **1280–1680** 量级）；**勿**在超宽视口下直接截全视口了事。
   - **事后裁剪**：`sips` / ImageMagick 仅裁灰边，**不得**误伤业务 UI。
   - **`fullPage: true`**：仅当需要纵向完整长页时使用；壳层索引优先 **视口 + 收窄宽度**。

4. **写回设计列**：按设计列模板填截图路径与场景标注，附「打开真实页面」链接。

### 设计列模板

```md
![](/prd/xxx.png)<br>
**场景预览：** xxx<br>
**状态说明：** xxx<br>
[打开真实页面](http://127.0.0.1:5173/xxx)
```

### 深链接规范

1. **页面级链接（必需）**：至少能打开到目标页面。
2. **模块 / 标题级链接（优先）**：若页面原生支持 hash、query 或滚动定位，则使用。
3. **场景级链接（可选）**：若页面原生支持通过真实参数直达具体 tab / 状态 / 场景，可继续细化。

只使用页面本身已支持的定位能力，**不要**为了 PRD 编造 query 参数、hash 或伪深链接。

### 本地 Demo 页面链接如何获取（真实 URL）

凡写入「打开真实页面」或 Demo 直达 Markdown 链接，须得到**当前本机可打开**的完整 `href` 再写回 PRD：

1. **启动 Demo**：在业务项目根目录执行 `npm run dev`（嵌套时多为 `prd-standalone` 的 `../`；多根工作区则为工作区内的业务文件夹）。**以终端输出的 Local 行为准**记下完整 origin（如 `http://127.0.0.1:5173`）；若端口被占用 Vite 会改用其他端口，**必须以本次终端输出为准**。
2. **对齐 path**：打开业务项目的路由配置（如 `src/App.jsx`，路径按实际业务根目录解析），找到目标页的 `Route path`（如 `/member-offer/config`），拼成候选 URL：`origin + path`。
3. **用浏览器工具校验（先「七 → 启用检测」：若已配置 Chrome DevTools MCP 则固定使用；否则 Cursor Browser）**：
   - **Chrome DevTools MCP**（**若「启用检测」通过，固定使用**）：`navigate_page` / `new_page` 打开 `<候选 URL>`，或在本机 Chrome 已开标签中用 `select_page` 选中后确认 `window.location`（可用 `evaluate_script` 读 `href`）。
   - **Cursor Browser**（**仅当** DevTools MCP 未配置或不可用）：`browser_navigate` 打开 `<候选 URL>`。
   - 若导航成功、页面可正常交互，可将该 **候选 URL** 作为写回 PRD 的链接（须与步骤 1 终端输出的 `origin` + 路由拼出的字符串一致）。若工具返回了最终 URL（如重定向后地址），**以工具返回为准**。
   - **无**可用自动化工具时，不得以猜测端口或路径代替；须在已启动 Demo 的浏览器中从地址栏复制完整 URL。
4. **无法使用上述工具时**：在已启动 Demo 的浏览器中打开候选 URL，从地址栏复制完整 URL。
5. **注意**：`prd-standalone`（PRD 阅读站，常见端口 6001）与业务 Demo（Vite 开发服务器，常见端口 5173）是两个不同 origin，**不可混用**。

### 禁止事项

- **不要**在 **100%**（或任意非 **67%**）页缩放下产出**设计列入库截图**；**不要**用 DevTools **`take_screenshot(uid)`** 代替 **「67% 标准成图法」**。
- 不要用占位图、手绘图、虚构 UI 替代真实截图。
- 不要把运行时临时标记写回源码。
- 不要编造不存在的页面链接或参数。
- **不要在设计列单元格里加「链接说明」「注意事项」「使用方法」等解释性文字**；说明类内容只属于本 SKILL 文档，不写入 PRD。
- 不要在没有用户要求时主动大范围修改 `设计/原型稿` 列中已有的截图。

## 八、Annotations 增强输入

仅在以下情况启用：

- 用户在编辑器里手动框了局部区域。
- 当前任务只想限定某个局部 UI。

使用规则：

- 只消费 `inScope=true` 的 region。
- 对每个输出列分别按 `generateColumns` 过滤。
- 看图优先读 `focusSrc` / `cropSrc`，不要重新解释整张大图。

## 九、执行流程

### 1. 定位主输入

- 确认 Demo 项目路径、运行地址、目标 PRD 文件路径。
- 若用户没给运行地址但项目正在运行，从路由、终端或页面入口定位。

### 2. 用 Demo 还原可见状态

- 字段、按钮、标签、布局、展示状态 → 以本地 Demo 当前实现为准。
- 代码里已实现的状态流转、前端条件展示、默认值 → 以 Demo 和源码为准。
- 若 Demo 与用户描述冲突，优先对齐用户目标。
- 需补设计列截图时：先 **「七 → 启用检测」**；**若已配置 Chrome DevTools MCP 则固定使用**，再按 **「七 → 67% 标准成图法」** — **强制 67%** + 视口 PNG + **`getBoundingClientRect`** 按比例裁切；**连接失败时先「七 → profile 占用重试」**；**仅当** DevTools 仍不可用再用 **`cursor-ide-browser`**，**同样强制 67%** 与等效裁切。

### 3. 用文档补隐藏逻辑

- 字段来源、状态条件、历史数据处理、后端规则、兜底逻辑 → 结合补充文档和用户描述。
- 隐藏规则不清晰时保守写法或列待确认。

### 4. 写回 PRD

- 读取当前激活文档 `.md` 的 Markdown 结构、表格格式、图片路径格式、Block 约定。
- 只在用户要求的范围内写回，以单个表格行为最小单位。
- 保证文档保存后能被前端正确渲染。
