# PRD 写作风格（prd-writing-style）

> 与 **`.cursor/skills/prd-spec/SKILL.md`** 併用：本 skill 管**怎么写得清楚、好审**；**prd-spec** 管**结构、解析、工具链、写回边界**。若冲突，以 **prd-spec** 与 **prd-writing-guard** 为准。

---

## 何时引用

- 用户 `@prd-writing-style` 或要求「按我们文风 / 习惯 / 润色交互逻辑」。
- 与 `@prd-spec` 一起写 PRD：先满足规范与表格语法，再按本节收束语气与密度。

---

## 语气与可读性（交付研发 · 强制）

> 与 **`prd-writing-guard.mdc`**「语气：交付研发 + 口语好懂」一致；落笔时与「禁入内容」同时检查。

**文档定位**

- 正文是**交给研发实现、可评审、可验收**的产品需求，**不是**写作过程说明，**不是**「和某环境对齐」的备注。

**表达怎么写（口语化 ≠ 不严谨）**

- **先让人听懂**：短句、一条说一件事；能用日常词说清楚就不用生僻词。
- **术语**：界面固有名词、品牌名可保留；**避免**为显得专业而堆「门控」「链路」「矩阵」等黑话；**确需**时用括号补一句人话（例：**会员生效范围**（管哪些会员能看到））。
- **禁止**把需求绑在「演示 / Demo / 本机 / 本地页面 / 快照壳 / 联调 / mock 环境」上——范围用**产品侧说法**（**商家后台**、**本期**、**配置页**、**编辑器内可见** 等）。细则见 **`prd-writing-guard.mdc`** 禁入第 2～4、8 条。

**与「正式」的关系**

- 这里的**正式**指：**交付物性质正式**（需求可落地、可评审），**不是**公文腔或论文腔。研发读起来应像**把话说清楚的说明**，不像教材目录。

## 图片 alt 文案（与 prd-spec 併用）

- **硬要求**（`[]` 非空、禁止裸 `![](...)`）见 **prd-spec·五 → 图片 Markdown alt** 与 **`prd-writing-guard.mdc`**。
- **格内图版式**（与列表）：`/prd/` 图须**单独成行**、行首即 `![`；**不要**写 `  - ![…](…)` / `1. ![…](…)` 等「列表前缀 + 整行仅一图」。见 **prd-spec·五 → 格内图片与列表**。
- **本 skill 写什么**：`[]` 内用**简短简体中文**概括画面，建议 **模块或场景名 + 界面片段 + 必要时状态**（与 **「小节标题命名」** 同思路：路径可读、少术语堆砌）。**一句内**说完；设计列若仅有图、无额外「场景预览」短注，**以 alt 为准即可**。
- **示例**：`![会员弹窗-折扣配置-自定义折扣已选](/prd/loyalty-member-offer-entry-card.png)`（具体以该图真实内容为准）。

## 列表层级格式（强制）

> 适用于交互列、逻辑列中所有「分组名 + 子项」结构。

**规则**：父级分组名（即有子项的层级标签）一律用 **`**加粗**`** 直接写，**不加 `-` 前缀**；子项才开始用 `- `；若子项还有下一级，用 `  - `（缩进两空格）。

**禁止写法（图 1 样式）**：

```
- 移动端
  - 位置：右下角、左下角；默认 右下角。
  - 距底边 / 距侧边：整数 px，范围 0～240；默认分别为 10、8。
```

「移动端」本身是分组名，不是一个独立选项，不应挂 `-`。

**正确写法（图 2 样式）**：

```
**移动端**
- 位置：右下角、左下角；默认 右下角。
- 距底边 / 距侧边：整数 px，范围 0～240；默认分别为 10、8。
```

分组名加粗即可，子项从 `-` 开始，视觉层级清晰。

## 交互列：结构与取舍

- **结构**：先用一句话概括**本次变更性质**，再分点展开。
- **【】与加粗**：**仅**界面上的 **按钮**、**链接式 CTA**（如 **【返回】**、**【保存配置】**）用 **【名称】**。**区块小标题**、**字段名**、**Tab / 卡片标题** 等一律 `**加粗**`，**不**套【】。**唯一例外（PRD 标签）**：hover 定稿必须用固定 **【hover 文案】** + 全角冒号后的定稿句（Markdown 源：`- **【hover 文案】**：`），**不得**因「【】仅用于按钮」而改成 **说明**（…）括号形式（语法见 **prd-spec·五 → hover**）。
- **不写的内容**（与列职责配合）：
  1. **截图已表达的**：结构、布局、控件位置、视觉样式——能看图的不复述。
  2. **设计稿职责的**：元素顺序、间距、按钮位置。
  3. **开发实现细节**：数据来源、字典对齐、灰显规则等——答案已隐含在已定稿的枚举与行为里时，不必单独开条（除非评审必须点名）。
  4. **顾客端条件分支**（展示路径随条件变）→ 归 **逻辑列**；交互只写后台配置面。
  5. **写作元说明**：不写「本段侧重」「与某节互补」「本节与下节分工」——只写产品事实；对照关系用 **节号**（如「详见 **2.1.2**」）或设计列截图。
  6. **静态固定文案**：界面上一眼可见、不随场景变化的标签 / 提示文字不必逐条抄写——看图即知。**只有两类文案值得写**：**(a)** 随场景或数据变化的**动态文案**；**(b)** hover / 聚焦等**交互后才可见**的文案（按 hover 定稿格式写）。
  7. **通用交互模式、自解释按钮与组件平台惯例**：Esc 关闭浮层、点击遮罩关闭、标题栏 × 等**行业默认行为**不必写入；标准模态（如离开确认、删除确认）的按钮若**从文案即可推断行为**（如「继续编辑」= 留在当前页、「离开」= 执行跳转），也不必逐个解释做什么。更广泛地：**Web 组件的标准交互惯例**——下拉 click / Enter / Space 展开收起、箭头图标表示可展开、Chip 含名称与移除、复选框勾选取消等——不必教科书式列举，开发者实现这类组件时自然遵循平台惯例。PRD 只需定义**本功能偏离标准模式的行为**。
  8. **渲染与样式实现指导**：CSS 定位策略（如「固定定位叠加层，避免被父级容器裁切」）、z-index 层级、溢出处理方式等——属开发实现决策。PRD 定义行为结果（如「面板不被遮挡」），不指导渲染方式。

**「说明文案」小节**（与 **2.1.2** 等仓库正文对齐）：模块内有一段与界面定稿一致、供配置方阅读的说明时，用 **`**说明文案**`** 单独成块。**写什么**：只写定稿句——可直接按「是什么 / 在什么条件下 / 建议配置什么 / 带来什么效果」分条（多条用多条 `-`）。**不写什么**：不写总起元说明（如「首段侧重…与…互补」）；**不要**另加一条解释「说明文案与预览示意如何分工」。与 **模块定位**、**清单行**、**预览示意** 等并列时，按模块真实结构拆分即可。

**图表悬停浮层**（曲线/热区等）：在 `交互` 用中文写行为与展示内容（**鼠标悬停** … 展示「…」）；禁 **X/N** 占位；可与字段侧 **【hover 文案】** 同源时交叉引用，避免重复粘贴。与**整数秒**配置字段联动时，浮层展示**整数秒**，不要求界面展示小数秒。

## 用语：禁止占位符与字母代词（交互 / 逻辑）

- 禁 **单字母、格式串**（N、YYYY-MM、C/B…）承载业务语义；用**可读中文概念名**，可加 **`**加粗**`** 作术语锚点。
- 端侧：**顾客端**、**商家后台**（或团队统一的消费者端/管理端）；禁 **C 端 / B 端**。
- 例外：界面固有英文、合法 URL、示例中的具体日期；说明「命名格式」时用中文拆段，不单写 **YYYY-MM** 教人猜。
- 运算：用中文动词与术语，禁 **A÷N** 式字母公式；可举阿拉伯数字验算。

## 业务概念与后台字段（推荐）

- **优先**用产品概念说清「在管什么」，**再**用半角括号对齐后台字段或标签，如 **会员生效范围**（**适用会员**）。
- **概念层**（优先用于 `逻辑` 列与索引口径）：先写判定维度（如「须 / 不做 **会员生效范围** 判定」），再展开条件。
- **字段级**（适合概念已明之后的细化）：直接对着某项写可执行条件（如「**适用会员** 不得为『全部会员』」）；**不宜**单条叠多重否定。
- **否定句**：直述「**不做会员生效范围（适用会员）判定**」即可，避免「不适用『…非…』类判定」等曲折嵌套。

## 初稿即简洁

> 本节是**第一次落笔**的取舍原则，用于从源头减少冗长；**不是**「先写长文再删」的事后压缩清单。

1. **列边界先划清**：`交互` 只写界面上可见、可操作的事实；`逻辑` 只写页后判定、换算、频控、过滤、准入。**禁止**同一句意思在两侧各写一遍（改几个同义词也算重复）。
2. **能「详见」则不重写**：与他节完全重复的口径只写 **「详见 ×.×.×」**；本节只保留**仅在本模块成立**的增量信息。
3. **加粗小节下控制条数**：非字段拆解需要时，不为「看起来完整」堆同义句。
4. **定稿与解释分工**：**说明文案**、**【hover 文案】**、引号内定稿句——**照抄定稿**；系统怎么算、何时刷新等用**一条逻辑 bullet** 收束，**不要**在 `交互` 里展开算法全文。
5. **禁止写作元说明**；信息不足时用 **「以产品约定为准」** 并给推荐值，**禁止**占位废话撑篇幅。
6. **多字段卡以字段名为轴**：每个配置项单独成条，下面只挂控件、取值、定稿；**禁止**一条 bullet 从左到右「流水账」扫整张卡。

---

## 不确定时的写法（与 prd-spec·四配合）

- 信息不足不瞎编；**待确认**写「xxx 待确认，推荐 xxx」；取值范围同时给推荐区间与默认值。
- **行业通行**（同类 SaaS 共识行为）可直接写定稿，不必套待确认。
- **禁用「以现网为准」** → 改为「以设计稿 / 接口文档 / 产品约定为准」等明确对象。

---

## 变更用语（无特殊用户文风时）

| 关键词 | 适用 | 要点 |
|--------|------|------|
| `全新功能` | 新页面、新模块或完整链路 | 从目标写起 |
| `原页新增` | 现有页增入口/字段/卡片等 | 显式写「新增」 |
| `功能迭代` | 已有能力增强 | 「调整/更新/补充」，勿假装全新 |
| `沿用现状` | 本次不动 | 写清保持原样 |

用户有固定文风时优先服从用户。

## 小节标题命名（建议）

- **格式**：`大模块名-子模块路径-功能名`，各段用 `-` 连接，**一律以纯中文路径语义为主**，**禁止**夹入英文技术短语作标题骨（如「Loyalty & Push」「前置与门控」）。
- **正确示例**：`会员弹窗-活动创建-折扣配置-自定义`、`会员弹窗-折扣配置-Loyalty 安装判断`（仅无合适中文替代时保留品牌名，仍以配置路径为主）。
- **应避免**：标题里堆砌「门控」「前置条件」「判定」「安装检测」等系统设计语言；改成需求侧可读说法（如「是否已安装 Loyalty 的说明与开关」）。
- **品牌/产品英文名**：仅在没有合适中文替代时保留（如界面固有 **Loyalty**）。

**章节序号**（与 **prd-spec·六**「章节序号与编辑器」「常见文档骨架与表格绑定」配合）：文档长、需评审指位（如「按 2.1.3 改」）时用 **2.1.3** 式；同一父级下强顺序的配置块特别适合带号。`##` 在「需求概述」「产品详细功能说明」等**父语境下各自从 1 递增**；插入/删节后顺延编号，并核对 `annotations.json` 中与 `sectionTitle` / `tableKey` / `rowKey` / `usageId` 相关的键。

## 自检（文风向）

- [ ] 分组名 / 层级标签是否为 **加粗**（无 `-` 前缀），子项才开始用 `-`？
- [ ] 是否避免占位符、元说明与交互/逻辑重复？
- [ ] 待确认 / 行业通行 / 「以现网为准」替换是否按本节？
- [ ] 小节标题是否路径清晰、少系统黑话？
- [ ] **【】** 是否仅用于按钮/CTA；hover 是否仍用 **【hover 文案】** 固定标签（见 **prd-spec**）？
- [ ] 若文档带章节号，插入/删节后序号与 **prd-spec·六** 所述 `h2`/表格绑定是否仍合理？
- [ ] 正文是否**未**出现 **演示环境 / Demo / 本机 / 本地（开发环境）/ 快照壳 / 联调 / mock** 等环境锚点（见 **`prd-writing-guard`** 第 8 条）？
- [ ] 句子是否**口语化、好懂**，避免论文腔与无谓黑话（见本节「语气与可读性」）？
